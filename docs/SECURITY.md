# گزارش امنیتی اولیه — DOZ ONLINE

تاریخ: ۲۰۲۶-۱۰-۱۷ · محدوده: نسخه 0.1.0 (فاز اول تولید)

## ۱. مدل تهدید و تصمیم‌های اصلی

| تهدید | کنترل |
|---|---|
| تقلب در حرکت‌ها (حرکت خارج از نوبت، بازنویسی صفحه) | همه حرکت‌ها از RPC امن `make_move` می‌گذرند: قفل ردیف اتاق (`FOR UPDATE`) + ۹ بررسی ترتیبی + محاسبه نتیجه روی سرور |
| حدس/سرقت کد اتاق | کد ۶ نویسه از الفبای ۳۱ نویسه‌ای (~۸۸۷ میلیون ترکیب) با `gen_random_bytes`؛ **کد اتاق به‌تنهایی مجوز حرکت نیست** — توکن ۱۲۸بیتی مجزاست |
| نشست توکن در دیتابیس | فقط هش SHA-256 توکن ذخیره می‌شود؛ توکن خام هرگز |
| افشای توکن در URL/لاگ/کانال‌ها | توکن فقط در بدنه HTTPS RPC ها؛ URL فقط شامل کد اتاق؛ broadcast ها projection امن بدون توکن است |
| دسترسی عمومی به داده‌ها | RLS فعال + صفر Policy مجاز + REVOKE از anon/authenticated؛ فقط ۲۰ تابع امن مجازِ اجرا هستند (تست شده: خواندن/نوشتن مستقیم جدول‌ها برای anon خطای permission denied می‌دهد) |
| SQL Injection | هیچ SQL پویایی در مسیر کاربر وجود ندارد؛ ورودی‌ها Type-Checked و Constraint-دار |
| XSS | React escaping + بدون `dangerouslySetInnerHTML` + CSP در `_headers` + اعتبارسنجی نام نمایشی سمت سرور |
| Clickjacking / MIME sniffing | `X-Frame-Options: DENY`، `X-Content-Type-Options: nosniff` |
| سوءاستفاده / DOS | Rate Limit滑动-پنجره‌ای در دیتابیس: ساخت اتاق (پیش‌فرض ۸/ساعت/IP)، ورود (۴۰/ساعت/IP)، لاگین مدیر (۱۵/ساعت/IP) |
| Brute-force مدیر | رمز bcrypt هزینه ۱۲ + پیام خطای یکسان + Rate Limit + Audit |
| جعل درخواست مدیر | هر تابع مدیریتی توکن نشست (۲۴ بایت تصادفی، هش‌شده، ۸ ساعته) را سمت سرور بررسی می‌کند؛ خروج → ابطال فوری (تست شده) |
| Race Condition | تراکنش + قفل ردیف + قید یکتایی `(room_id, symbol)`؛ ورود هم‌زمان دوم → `ROOM_FULL` (تست شده) |
| رویدادهای Realtime دست‌کاری‌شده/قدیمی | کانال فقط اعلان است؛ وضعیت از RPC خوانده می‌شود؛ snap shot های قدیمی با `version` دور ریخته می‌شوند |
| SQL اضافه‌بار انقضاها | pg_cron هر ۳۰ دقیقه + پاک‌سازی احتمالی در `create_room` |

## ۲. `SECURITY DEFINER` — ملاحظات

- همه توابع حساس: `set search_path = public, pg_temp` (بدون اسکیمای قابل تزریق)
- فراخوانی pgcrypto با نام کامل اسکیما (`extensions.digest` و…)
- `EXECUTE` از `PUBLIC` گرفته شد و فقط به `anon` روی لیست‌سفید داده شد
- هیچ `EXECUTE ... USING` پویا یا `FORMAT` با ورودی کاربر در مسیر دیتا وجود ندارد

## ۴. ریسک‌های شناخته‌شده / توصیه‌های بعدی

1. **XSS و توکن در sessionStorage** — توکن بازیکن در دسترس جاوااسکریپت است. کاهش‌دهنده‌ها: CSP سخت‌گیرانه، نبود وابستگی رندر خام. بهبود آینده: HttpOnly Cookie با SameSite روی دامنه مشترک (نیازمند proxy یا Edge Function).
2. **Rate Limit مبتنی بر IP** — پشت NAT مشترک ممکن است کاربران سالم را محدود کند؛ حد از پنل قابل تنظیم است. گام بعدی: Turnstile برای create_room در صورت سوءاستفاده واقعی.
3. **CSP شامل `'unsafe-inline'` برای style** — برای Vite/فونت لازم بود؛ حذف آن با استخراج کامل استایل‌های بحرانی در نسخه بعد.
4. **حداکثر ۹ حرکت/بازی و قیدهای سخت دیتابیس** — نفوذ به سطح SQL هم نمی‌تواند وضعیت نامعتبر بسازد (CHECK constraints روی board، status، سلول‌ها).
5. هیچ سیستمی «کاملاً امن» اعلام نمی‌شود؛ این گزارش صرفاً کنترل‌های اعمال‌شده و آزمایش‌شده را فهرست می‌کند.
